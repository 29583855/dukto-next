# 连续接收线程交接修复

创建日期：2026-11-25；更新日期：2026-11-26。范围为独立移动项目，不修改桌面及Dukto原版。

## 现象与原因

原始f20c51ab arm64 APK在Android15模拟器安装和两批接收通过，但32批连续测试第5批没有落盘或任务记录；前4批成功，runtimeErrors为空。测试通过ADB TCP转发直连生产APK的4644端口，无重发，也没有重启接收器。

`LegacyJob::receive()`提交文件并关闭TCP连接后，还需要执行结果信号、数据库释放及线程退出。`LegacyListener`直到收到排队的`QThread::finished`才释放活动槽位。发送者收到EOF便发送下一批时，旧线程尚在收尾，原逻辑会直接拒绝下一连接。

确定性回归用信号阻塞点强制保持“客户端已收到EOF、旧线程仍未退出”。旧代码run45640879855/job139298852599编译成功，执行报`next batch rejected after previous successful EOF`，与APK丢批症状一致。原失败证据保留于evidence/receiver-handoff-baseline-20261125.json。

## 修复设计

1. 始终只启动一个接收线程。
2. 活动线程存在时最多保留一个原生socket描述符，使用接收超时限制等待时长；第三个连接立即关闭。
3. 旧线程实际退出后，将等待描述符交给下一工作线程；监听主线程不读取网络正文。
4. 取消、超时及析构均关闭等待连接；忙时拒绝修改接收目录。
5. 描述符只在其工作线程创建QTcpSocket；测试同步对象的生命周期覆盖工作线程。

没有修改R6格式、端口、文件覆盖规则或接收成功的含义；R6没有额外的发送端摘要确认，本次不添加不兼容扩展。
