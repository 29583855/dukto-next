# Windows 向 Mac 发送失败：代理类型不支持

更新日期：2026-11-10。

## 本次定位

用户截图的 Windows 发送历史显示 `The proxy type is invalid for this operation`，Mac 没有接收提示；同一截图显示 Mac 向 Windows 的两次传输已经接收完成。因此这次具体故障发生在 Windows 主动发送连接阶段，数据尚未到达 Mac，不能归因为 Mac 接收文件写盘失败。

旧实现的 R6 传输 `Wire` 内部 `QTcpSocket` 保持默认代理，可能继承系统/应用 HTTP 缓存代理。缓存 HTTP 代理不支持 Dukto 的原始 TCP 文件传输，Qt 在连接阶段就拒绝操作；HTTP CONNECT 或 SOCKS5 代理还可能把局域网目标错误地交给代理服务器。

## 修复

R6 文件、目录、文本、剪贴板和截图共用同一传输核心，现统一在连接或接管接收描述符之前设置 `QNetworkProxy::NoProxy`。两端通过目标 IP 和 TCP 端口直接连接。该设置只影响软件自己的 R6 套接字，无需用户关闭或修改系统代理。

按用户最新要求，默认 TCP/UDP 端口继续为原版使用的 4644，头像使用 TCP 4645。已移除尚未交付的自动备用端口选择及备用端口广播；同机运行时先退出原版或另一实例，冲突会明确提示。显式 `--port` 开发/脚本参数仍保留。

## 使用与排查

1. 退出旧版 Next，完整解压修复包后启动；Windows 请保留同目录 DLL、plugins、qml 等依赖，不能只复制 EXE。
2. 同机先退出原版 Dukto，再打开 Next；两端均检查底部显示接收端口 4644 就绪。
3. 在 Windows 选择 Mac，发送一个小文件，再检查 Mac 最近记录与接收目录。成功记录需要显示接收完成；发送端的本地完成本身不是远端写盘确认，原版 R6 协议没有远端校验确认。
4. 若连接超时，检查 Mac 防火墙/本地网络权限与 TCP 4644 可达性；发现使用 UDP 4644，能发现设备并不代表 TCP 传输一定放行。若 Mac 已提示接收错误，再按其目录权限/剩余空间错误处理。

## 验证方法与状态

新增四组真实网络回归：HTTP 缓存、HTTP CONNECT、SOCKS5、系统风格代理工厂。测试使用非回环 IPv4，先确认未指定直连的 Qt 套接字失败，再从生产 GUI 控制器的拖放入口发送 2 MiB 以上二进制、中文/空格目录、零字节文件、空目录及中文文本，核对接收结果与实际内容。

## 2026-11-10 验收结果

源码提交：`169e04df4f742f3ad19f9ef75057cf3982e744b9`。四包均核对官方工件摘要、包内清单、对应源码和构建输入；完整核心无失败或跳过。Qt5 JUnit会合并参数行，代理四项另从实际文本日志逐行核对PASS。

每包510份应用源码均对应同一Git提交。Windows检出的410份UTF-8文本仅有LF到CRLF转换，逐份还原后Git blob一致；包内清单和构建输入摘要仍按实际CRLF字节核对。第三方原件不允许换行归一化。

Windows旧发行包已在本机真实系统代理环境复现退出码3、connect阶段代理类型不支持，独立接收端没有收到连接。修复包在同一机器、同一非回环IPv4环境通过独立Python R6解码和SHA-256正文比对，证明Windows主动发送恢复。

Mac两种架构的全部原生镜像最低系统版本均不高于12.0；实际CI运行机为macOS15，客户12.7.6实机仍需确认。Linux最终包在X11/Wayland均通过。Windows最终包含DLL并在系统PATH迁移运行验证通过。

两台客户物理Windows/Mac的现场局域网复测仍待确认，不能用同机原生回归代替。先前测试硬编码英文错误文字导致的失败、旧Intel安全通道测试失败及被替代运行均保留在交付目录“验证记录/历次构建”，未改写为成功。
