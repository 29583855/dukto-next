# 界面内存增长修复

日期：2026-11-11。状态：根因已定位，修复与回归验收进行中。

## 现象和原因

Windows客户端打开服务器页面、文本框获得焦点后，空闲状态下仍可能持续增长约17–20 MiB/s。此前系统事件2004记录过测试进程约13 GiB的提交内存。上传文件选择器的堆损坏是已经单独修复的另一项缺陷。

本次在隔离进程中跟踪大块分配，调用栈反复出现`QAccessible::setActive(bool)`、`QQuickScrollBar::accessibilityActiveChanged(bool)`、`QObjectPrivate::connectImpl`。Qt 5.15的滚动条实现收到每次`active=true`通知都会再次连接辅助功能的`increaseAction`和`decreaseAction`，没有对相同状态去重。Windows的辅助功能查询会再次激活通知，即使状态已为启用，也可能继续走这条路径。

因此，增长来源是同一滚动条累加辅助功能信号连接；这种重复连接还可能使一次辅助功能滚动动作执行多次。不能把文件传输、输入法或Microsoft Edge写成已确认的故障来源。具体是哪一个系统组件发出每条查询，不影响控件必须能安全处理重复激活的要求。

## 修复设计

新增`StableScrollBar`继承与Qt 5.15运行时匹配的滚动条模板。每个实例记录最近激活状态，仅在首次通知或状态发生变化时转交Qt处理。停用仍由Qt断开连接，再启用时正常连接；对象销毁后状态随实例释放。

使用应用内局部样式替换滚动条模板，覆盖页面显式声明的滚动条和ScrollView隐式生成的滚动条。其余控件沿用Qt默认样式。保留辅助功能、鼠标和触摸滚动；没有过滤Windows消息、关闭辅助功能或变更传输协议。

兼容类使用Qt模板私有开发头，因此编译和运行的Qt必须匹配。Ubuntu构建额外安装`qtquickcontrols2-5-private-dev`；Windows和macOS使用原生Qt 5.15开发环境。编译标准保持C++14。

## 验收计划

- 保留旧包增长曲线、分配栈和诊断失败记录。
- 加载生产Main.qml与服务器弹层，核对所有滚动条均使用兼容类。
- 重复激活5000次，每个辅助功能动作仍只移动一个步长；停用/重启用及启用后新建控件同样验证。
- 四个平台原生编译并运行回归与最终包测试。
- Windows最终包执行持续前台运行、输入框焦点、页面切换和上传下载复验，记录私有提交内存。

各项取得实际证据后补充结果。隔离诊断中的动态钩子和资源替换程序不作为交付修复，旧失败记录不删除。
