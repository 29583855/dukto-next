# 局域网发现与原版 Dukto 共存

更新日期：2026-11-10。

## 截图问题的原因

截图中 Windows 提示错误 10048，Mac 提示错误 48，两者均表示接收端口已占用。原版 Dukto 默认使用 TCP/UDP 4644、头像 TCP 4645。在旧版 Next 中，TCP 4644 绑定失败后会直接跳过设备发现的启动，因此会一直显示“等待局域网设备”。同一台机器的原版仍在运行时，它仍能发现远端设备，不能据此推断 Next 的发现也已启动。

另一个问题是旧版 Next 独占 UDP 发现端口；即使手工更换端口，它也只监听自定义 UDP 端口，没有同时监听标准 UDP 4644，因而接收不到其他实例发往标准端口的广播。这两处已一起修复。

## 修复后的启动行为

- 直接打开 Next 时，优先使用 TCP 4644；若已被原版或其他进程占用，依次尝试 4648、4650，直到 4678，共 16 个固定备用端口。状态栏显示实际接收端口。备用范围避开软件服务器模式的默认 TCP 4646。
- TCP 接收保持独占，文件不会因端口共享被交给另一个程序。头像使用实际接收端口加一，头像失败不影响设备发现和文件传输。
- 实例尝试共享监听标准 UDP 4644；自定义接收端口另外监听同号 UDP，接收定向回复。Mac 上原版默认绑定可能完全不允许共享，此时 Next 仍保留实际接收端口，每 5 秒向标准端口和固定备用端口范围发送有界发现请求，两端均退让到备用端口也可以直接互相发现。公告使用原版 Dukto R6 的 1/2/4/5 格式，公布实际接收端口。
- 手动指定 `--port` 时严格使用指定端口，冲突会报错，不自动改端口。CLI 的接收和服务器模式也保持明确的端口语义。
- 兼容原版退出包的固定 `Bye Bye` 正文；畸形数据报仍被拒绝。

## 更新与使用

1. 两台机器都退出旧版 Next，换用本次“局域网发现修复版”。Mac 按“关于本机”的芯片选择 Intel 或 Apple Silicon。macOS 最低构建目标仍为 12.0，原来的 macOS 12 安装说明继续适用。
2. 直接打开程序即可自动发现；若需要与原版同时运行，先打开原版，再直接打开 Next。不要给 Next 附加固定的 `--port 4644` 参数。
3. 观察底部状态栏。正常应显示“就绪 · 接收端口 …”，或“4644被占用，已使用接收端口 … · 自动发现已启用”。点击“刷新设备”立即发送发现请求。
4. 在设备列表选择对方发送。手工通过 IP 连接时，如果对方使用备用端口，请输入 `IP:实际接收端口`，例如 `192.168.1.20:4648`。

## 仍无法发现时

两端需要位于可达的 IPv4 广播网络。Windows 首次弹出防火墙提示时允许应用在所用局域网通信；macOS 按系统提示允许应用联网，在提供“本地网络”权限的系统中也应允许。原版与 Next 是不同应用，原版已被放行并不表示 Next 也已被放行。

程序不会自动修改系统防火墙。手工管理规则时，发现需要 UDP 4644、实际接收端口的 UDP；传输需要实际接收端口的 TCP，头像另用实际端口加一的 TCP。只对可信局域网开放所需端口。无线 AP 隔离、访客 Wi-Fi、跨 VLAN 或 VPN 路由也可能阻止广播。

如果仍提示端口不可用，检查是否手工指定了被占用端口，或备用端口范围已全部占用。截图中的端口占用错误应先解决，不能只反复点刷新。
