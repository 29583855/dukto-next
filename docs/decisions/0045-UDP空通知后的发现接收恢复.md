# UDP 空通知后的发现接收恢复

日期：2026-11-06。生产修复和原生资格按精确提交回执记录。

本机 Alpine/Qt 5.15.18 的 R90 冻结构建有两个发现用例失败：持续发现链没有触发让出计时器，以及多地址设备的 Goodbye 没有删除最后地址。原运行的 22/23、原 XML 和日志保持不变。

独立 C++14 探针按时间分开发送 1、2、32 字节数据报，QUdpSocket 均能接收。使用 Discovery 原接收逻辑的独立副本记录到：Hello 在真实可读通知和排队续读中排空后，仍出现一次可读通知，此时 MSG_PEEK 返回 EAGAIN、poll 不可读。原循环因 hasPendingDatagrams=false 没有调用 receiveDatagram。稍后的两个 Goodbye 在内核中排队，poll 可读、Qt 的 hasPendingDatagrams=true，但没有新的 readyRead。末尾强制调用一次原 read 才能读取并删除地址。

Qt 5.15 分支的参考源码显示：未缓冲 socket 的通知在 hasPendingData 已置位时会禁用读通知；QUdpSocket::receiveDatagram 使用显式非负最大长度时，即使底层读取失败，也清除该状态并重新启用通知。这份上游分支文件用于解释探针结果，不声称是本机 Qt 5.15.18 的精确对应源码，也不作为第三方对应源码交付证据。

修复后的每轮处理至少尝试一次 receiveDatagram(1024)，包括队列已空的迟到通知。无效数据报立即退出；后续读取仍受 64 包和 5ms 处理时间片限制。第一读保证先于时间片退出，因此不是硬实时的 5ms 墙钟承诺。只有队列仍有数据时才排一条续读事件，空队列不排轮询；未来数据由恢复后的可读通知处理。空数据报、畸形 Goodbye、签名/地址数量和长度限制不变。

独立修复副本中，空通知实际执行了一次无效读取，之后两个 Goodbye 均各自触发 readyRead，并在任何强制对照读取之前删除相应地址。这限定了探针实例中通知停滞的原因，不追溯证明所有历史发现失败都只有同一原因。完整生产验证仍使用原来的两个核心用例，保留 5000 次变更及原 5s/10s 门槛；本机独立构建还重复运行这两个用例，不通过增加超时取得资格。

诊断副本及原始输出分别保存于 `docs/validation/2026-11-06/discovery-r92-notification-probe/` 和 `discovery-r92-empty-notification-probe/`。Windows、Alpine 和云端各平台结果独立收验；未完成的运行不记为通过，原 R90 失败不改写。
