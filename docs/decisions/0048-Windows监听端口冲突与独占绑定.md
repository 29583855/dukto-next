# Windows 监听端口冲突与独占绑定

日期：2026-11-06。C++14/Qt5；适用于 R6 接收、TLS 服务器和头像 HTTP 服务。

R94 双 Windows GUI 联测出现文本窗口未打开。为原等待增加诊断后，同一失败显示接收事件为空、历史为空、客户端连接被对端关闭。独立 TCP 端点记录进一步确认：UCRT 实例在 64798 监听传输、64799 监听头像，MSVC 实例同时报告在 64799 监听传输，实际连接进入 UCRT 的头像服务。原日志和端点记录保存在 `docs/validation/2026-11-06/text-view-r94h-windows/`；更早失败也保留，不改写为成功。

共用 `TcpListener` 在 Windows 创建原生 Winsock socket，绑定前设置 `SO_EXCLUSIVEADDRUSE`，成功监听后交由 Qt 管理接收通知和描述符。默认 Any 保留 IPv4/IPv6 双栈，显式 IPv6 监听保留独立地址族行为。Qt 以外的平台继续使用原 Qt 监听。三个产品监听入口统一接通，CLI 和 GUI 使用相同核心实现。

回归还确认：旧 Qt 已存在的共享通配监听，在部分地址组合下仍允许后来者执行独占 bind。因此固定端口绑定前及监听后，另核对同地址族的重叠监听端点；遇冲突、系统查询失败或超过有界表大小时明确失败，不换端口、不回退共享。原生表最多 8 MiB，表大小变化至多重读三次。系统临时表及内核对象尚不能代替整个应用的全局资源预算验收，也不把快照查询当作对任意外部程序竞争行为的形式化证明。

测试覆盖 IPv4→双栈、双栈→IPv4、通配→指定地址、相同 IPv6，以及原 Qt 先监听、产品先监听、原 Qt 在同地址族后尝试加入。冲突后原服务必须仍能接收真实字节；原服务关闭后同地址端口可重新使用。独立 IPv4/IPv6 监听与双栈实际连接分别验证。首次适配器未完全拒绝旧 Qt 共享监听的失败单独保留，只有最终回归通过才标记这一范围完成。

GUI 复制测试共用系统剪贴板，两个 Windows 工具链按顺序执行完整业务回归；端口冲突由上述核心测试明确构造并验证。接收文本分页本身的段落限制、全文复制和历史重开仍按决策 0047 单独验收。R93 Intel Mac 恢复测试失败继续保留，不由本次 Windows 修复推断解决。

完整回归另确认一个未消除的系统边界：产品IPv4独占监听已经存在时，外部旧Qt后来创建跨地址族双栈共享监听仍可能成功。该失败保存在 `text-view-r94-final-windows/ucrt/QtTest/core-tests.log`，不声称已阻止任意外部程序后来跨族劫持端口。最终测试明确验证本软件三个入口之间的冲突拒绝、已有旧Qt端口的启动前/后检测，以及同族外部重绑；这项更强的跨族外部竞争保证仍未验收。
