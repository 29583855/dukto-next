# 持久跳过准备决策

日期：2026-11-05。状态：`DurableReceive` 准备层已实现，Windows UCRT/MSVC 已实际验证。公开 skip、协议正文裁决和最终处置确认仍待接入。

`prepareDisposition()` 返回目标相对路径、是否跳过及跳过根序号。已有字符串 `prepare()` 遇到内部 Skip 明确拒绝，避免调用者丢失跳过标记并继续发送正文。CLI、远程上传/下载与任务创建只接受已开放策略，不允许产生无法恢复的半成品任务。

跳过日志使用版本三绑定任务 UUID、完整冻结强清单、策略、目标根路径及原生根身份。默认 rename 的旧版本一和 fail/overwrite 的版本二保持原格式。新 Skip 日志的基本表、绑定、逐项准备表及失败表在同一 FULL 同步事务建立；已有日志不补建损坏的缺表。

每项按冻结清单顺序写入 `receive` 或 `skip`。记录绑定源条目、原相对目标、跳过根及直接冲突对象的原生身份。普通文件和目录只有类型、路径、安全访问与活动预约核对通过才可跳过；不跟随链接。直接冲突时持有目标原生句柄和预约直到决定提交，最后一次取消/授权检查后再次核对根与目标身份。Windows 通过不共享删除固定对象；POSIX 在提交前重新验证路径，不能声称阻止了外部任意改名。

父目录已跳过时，后代只沿磁盘源路径唯一索引继承跳过根。既不枚举目标后代，也不创建其目录或正文。每项准备决定都先持久提交，再返回调用者。进程在提交后、调用者收到结果前退出，恢复仍返回原决定；原目标后来被删除或替换也不会改为复制。

准备 `receive` 只表示允许继续原接收流程，不能当作已复制。普通文件仍须全摘要、数据同步、原子发布和原日志确认。`open()`/`openSparse()`/`openConcurrent()` 不能为缺少原准备记录或已跳过的项目打开正文。最终 `copied`/`skipped` 仍由独立的 [0018 处置日志](0018-持久逐项处置日志.md) 表达；当前尚未自动衔接两者，也没有新协议最终确认。

恢复按最多 100 行分页重验序号、源索引、规范 JSON、条目和父子跳过根。源字段最多读取 4,097 字节、规范记录最多 65,537 字节，父项也执行相同字段检查。没有递归调用或驻留全部后代。每页、每项都有取消/授权检查；撤销后关闭连接和任务锁，下一执行者可重开。SQLite 缓存仍使用 1 MiB 授信，页数目标 256 MiB；全局配额与回收另外验收。

现阶段的明确边界：准备已决定接收之后，若目标在打开或最终提交时才出现，继续按显式冲突失败，保留原件及本任务临时证据。尚未实现这一阶段的持久最终跳过裁决。因此公开 skip 保持拒绝，不能用准备层通过替代整个 R03 验收。
