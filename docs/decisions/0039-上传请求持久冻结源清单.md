# 上传请求持久冻结源清单

日期：2026-11-06。

GUI 和 CLI 在新上传请求中先建立 `UploadManifest`，完成扫描和强摘要后，在受保护的 transfers 状态根保存清单数据库与原子冻结记录。包装对象持有独立请求锁，覆盖本地准备、认证、全部网络重试和最终确认；原上传请求锁和任务锁继续核对网络操作身份。

冻结记录绑定请求 UUID、服务器 UUID、客户端 UUID、共享、目标相对路径、冲突策略、按原顺序规范化的绝对源根摘要和源根数量。完整路径清单留在磁盘，不放进 JSON 数组。数据库中的本机 source 字段另以逐项、带长度的 SHA-256 绑定；公开强摘要继续只包含协议内容，绝对源路径不会传到远端。

相同请求重开时，只读重算清单公开强身份和本机源映射摘要，不枚举或打开当前源目录。原请求的文件集合和内容身份保持冻结；扫描后新增文件须使用新请求发送。后续生产传输及历史确认继续核对所需复制源的内容，不能把“清单重开成功”当成“源文件仍然有效”。原已跳过项的历史确认可在源被删除后进行，前提是原处置证据完整且一致。

记录缺失而数据库仍在、记录存在而数据库缺失、清单损坏、源映射变化或请求参数变化时，拒绝执行并保留原证据。正常扫描取消或失败只回收本次确认创建且尚未发布冻结记录的库。进程被强制终止在发布记录前时可能保留未配对数据库，后续明确报错，不能自行覆盖；此类残留的安全管理属于尚未完成的全局预算与回收工作。

较早版本只有 upload-request 绑定、没有持久源清单的请求，仍需要原源完成首次扫描；上传内核继续按原绑定核对清单摘要和目标，不自动升级其原计量契约。新状态的跨重启冻结从本版本开始，不能倒推证明旧版本曾持久保存源清单。

每次仅处理一条源映射，使用原清单的有界 SQLite 缓存及 256 MiB 单库磁盘上限。扫描、只读重验和映射散列都响应同一取消源和操作总期限。持久库不在正常操作结束时删除，多个历史请求的全局磁盘预算、保留期及安全回收仍须另行完成。

验证覆盖 206 项全跳过源目录删除后重开、复制源缺失拒绝、并发占用、主体/目标/策略/源根变化、映射篡改、缺失原件、取消回收及 SQLite 连接释放。真实 CLI 覆盖重启恢复发送回执、冻结后新增文件、原正文变化拒绝、原库字节保持；真实 TLS 的 GUI 面板重建后通过 resume 复用原任务，并拒绝已改变的复制源。各项最终结果和首次编译失败由本轮验证回执记录。

本项不启用公开 skip。其能力协商、GUI/CLI 选项、公开跳过的端到端与故障资源验证继续；完整项目 `deliveryComplete=false`。
