# 逐项接收失败证据

日期：2026-11-05。范围：新版 rename/fail 接收器的逐项历史原因，以及 GUI/CLI 分页展示。完整四种冲突策略、失败处置汇总及最终确认绑定继续按 0009 实施。

此前，批次会返回 4/conflict，但若冲突发生在创建文件或目录接收行之前，逐项页只有 `not-executed`，无法辨别这项已失败还是尚未处理。现在，接收器将确定的本地失败单独绑定到冻结清单的具体条目，查询同时返回持久复制状态和最近一次失败证据。

## 持久化与完成

在原接收 SQLite 日志增加 `item_failures` 旁表，主键为清单 ID；每项最多保留最近一次原因，不在内存保存文件列表或不断累积重试历史。旁表沿用原日志的缓存授信、同步事务和 256 MiB 磁盘上限。打开接收执行者时，先核对原任务、策略、强清单和接收根身份，再事务化增加旁表；原 files/directories/blocks 格式保持。

公开证据含版本 1、阶段 `prepare|open|write|finish`、错误码 4/5/6、受限的错误类别和 `resolved`，不保存错误消息中的路径、临时名称、凭据或文件内容。数据库行另保存该项完整公开强清单信息，读取时与原清单逐字段核对，拒绝被换成另一文件的原因。整数先按 64 位核对类型及枚举范围，再转换为公开数值；小数、字符串和超过 32 位的伪合法值不能通过。

文件或目录成功完成时，完成行与该项既有失败的 `resolved=1` 在同一同步事务提交。历史原因不会被成功清空。若后续恢复时发现已提交内容被外部改写，新错误重新置为未解决；`copied` 仍只代表历史提交记录，`currentContentVerified:false` 保持明确，不把历史成功用于证明当前内容。

## 归因边界

只记录接收器在准备路径、打开/恢复、写入/摘要校验及最终提交期间直接抛出的本地权限、磁盘、完整性错误。网络中断、用户取消、会话/批次权限检查、尚未进入接收器的协议错误或进程直接退出，不推断为某一个文件的失败；并行窗口中的其他项目不继承该项错误。

错误记录本身可能因磁盘满、日志损坏或资源不足无法写入，此时继续传播原始传输错误，不能以附加记录失败掩盖原错误。`lastFailure:null` 仅表示没有可用的已记录原因，不能推断从未失败、未执行或已经成功。这个子项没有完成完整的失败覆盖矩阵、磁盘满持久证据保障及逐项处置总计。

## 查询与兼容

能力 `task-item-failures-v1` 明确声明服务端提供本扩展。沿用 `task-items-v1` 的 v1 页和原请求，新增可选字段，既有 disposition 枚举保持：旧客户端仍可读取原复制状态，新客户端在能力存在时严格验证附加字段。旧服务器不声明能力且不提供字段时，新客户端保留旧查询行为；不能伪造远端原因。

| 字段 | 含义 |
| --- | --- |
| `failureScope:"receiver-local"` | 仅接收器确定的本地历史原因 |
| `failureEvidenceAvailable:true` | 本页只读快照存在原因旁表；不承诺所有异常均能记录 |
| `failureEvidenceAvailable:false` | 缺少日志、旧日志没有旁表或接收明细不可用；查询不迁移日志 |
| `lastFailure:null` | 该项没有可用原因记录；不能推出没有失败 |
| `lastFailure:{version,phase,code,stage,resolved}` | 最近一次绑定该项的原因；resolved 表示该错误之后已由接收器成功完成 |

上传读取服务端接收日志，下载读取原本机接收日志；身份、共享授权、原请求、本地根和清单绑定沿用 0010。每页仍最多 100 项且小于 64 KiB，逐项按主键读取，不扫描整棵树，不读正文，翻页不改变任务修订、接收状态或失败记录。

GUI 以中文展示准备目标、打开或恢复、接收与校验、最终提交及对应原因，同时显示原检查点。普通 CLI 在原条目后追加 `lastFailure`，JSONL 提供完整结构。现有复制状态与失败原因分别保留；全面的 `failed/skipped/not-executed` 处置汇总及最终确认仍另行实现。
