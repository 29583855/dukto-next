# 实际传输完成处置接线

日期：2026-11-06。

## 问题与范围

逐项处置日志已有独立验证，但实际服务器传输和客户机下载原先没有写入该日志。字节进度相等不能证明空目录、空文件以及每个最终名称都已完成，也不能作为后续跳过策略的完整批次结果。

本次先把现有公开的 `rename`、`fail`、`overwrite` 三种策略的实际 `copied` 结果接到 `DispositionJournal`。公开 `skip` 继续拒绝；独立接收核心支持跳过不代表协议、任务和界面已支持跳过。

## 完成记录与恢复

- 服务器上传在接收核心确认条目完成后记录实际发布名称。服务器下载在客户机确认该条目后记录对端返回的实际相对名称。
- 客户机下载在条目完成后先持久记录，再发布文件完成事件。服务器和客户机都在整批成功返回前要求处置日志完整匹配冻结清单。
- 单通道和多通道共用有序完成回调；16 项准备窗口内的准备、已接收部分数据以及失败项都不能提前记为 `copied`。失败保留已完成的连续前缀。
- 最终确认丢失后，已完成下载重试必须重验实际文件及接收日志，然后补齐或核对处置日志。目录使用其实际预约结果；普通文件使用 `finish()` 返回的最终名称，不能使用 `prepare()` 返回的原始候选名称。
- 日志重验按页处理并响应取消。下载本地日志操作不要求 socket 仍处于连接状态：完整最终帧可能已经到达缓冲区，而对端已正常关闭；最终成功仍须实际读取和严格校验该任务确认。
- 已有处置内容不一致必须拒绝改写。旧版已完成下载没有处置日志时，仅在实际清单与接收证据全部重新通过后创建。

## 资源与证据

日志沿用 1 MiB 全局 SQLite 缓存授信、256 MiB 单日志磁盘上限、FULL 同步和有界分页，不在内存中累积整批结果。新增真实 CLI/TLS 专项核对三种策略、1/4/16 通道、双向、跨窗口、Unicode、空项、多块文件、重试及失败前缀；确认丢失和进程故障专项另行核对相同处置。通过结果由验证文档引用原报告，不在本决策文档预先标记通过。

## 仍需完成

该阶段不改变线格式，也没有对等交换处置摘要。客户机上传尚无发送端本地处置日志。服务器已完成任务的历史状态查询及提前返回仍沿用旧行为，不能据此宣称对旧任务强制重新生成全部处置。
