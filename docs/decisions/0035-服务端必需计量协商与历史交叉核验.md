# 服务端必需计量协商与历史交叉核验

日期：2026-11-06

状态：服务端实现及双Windows工具链完整核心/十六份真实专项已验；原生CI按精确提交继续。普通客户机尚未启用新契约，公开 skip 仍关闭。

服务器新增 disposition-progress-v1 能力。对端必须在当前连接的 Hello 声明此能力，创建时再显式提供 dispositionProgress=true，并同时启用 byteProgress=true、dispositionSummary=true。未协商、非 true、缺依赖及额外字段均在创建任务前拒绝。现有 rename、fail、overwrite 允许选择此契约；skip 仍由公共策略入口拒绝。

新契约创建版本三任务并初始化必需零计量，绑定原请求摘要，不能在重试时降级为旧模式。进度交换使用严格十三字段，进度观察者验证身份、规范数字、单调性和守恒后，服务端在同一控制线程通过 recordAccounting 持久保存十个计数与逻辑进度。相同快照不重复更新；空文件和目录处置即使不增加字节也会推进计量。旧纯字节任务继续使用原路径，普通客户端暂不声明新能力，因此升级后既有请求身份保持。

本阶段把扩展进度和逐项跳过帧分别处理。三个既有策略仍使用兼容的文件确认帧；后续公开 skip 还须接通显式逐项处置、客户端请求契约、历史跳过源删除和条目/GUI/CLI。本次不把未接通的客户端功能宣称为完成。

提交前将任务计量中的复制/跳过字节及四类条目数，与独立逐项日志生成的完整处置摘要交叉核对。历史完成重试也进行相同核对；即使持久计量的字节和条目总数守恒，错误的文件/目录分类也必须拒绝。历史任务、清单、接收及处置证据不能因拒绝而被修补。

独立测试发现任务库在每次打开时重复设置 user_version=2，会改写 SQLite 文件头的变更计数及最后写入版本。改为只在架构迁移事务中设置版本；真实版本一迁移仍原子执行。损坏历史计量拒绝后逐字节核对任务库和处置库，以实测检验该边界。

验证使用独立 Python TLS 对端，实际发送/接收106项跨页清单、中文路径、空文件/目录和超过8MiB的两块正文；三个策略双向完成并重连同请求，直接核对任务数据库的版本三契约、固定快照和独立处置摘要。另检查任务契约降级、历史分类篡改、未协商及缺依赖字段，以及六字段混用、额外字段、非法数字、错误任务/清单、未同步复制和旧策略伪造跳过。

恶意进度可能使安全通道主动中止。测试只接受完整帧之间的断开，拒绝截断和超时，并独立核对服务事件错误、任务状态和原零计量；规范数字错误2按既有规则保留 interrupted，身份/计量错误6进入 failed；不能以连接断开本身作为校验通过。执行失败原件保留，最终资格按精确提交和独立运行报告记录。
